## Scope

This probe answers one question before Conductor Stage 1 writes a state schema or
changes a mutator: can the exact supported Herdr release expose every identity
field required to distinguish a Conductor pane from a foreign, stale, or recycled
pane?

The probe used a disposable Git repository, a disposable Herdr workspace, and one
explicitly named Pi agent. It inspected plugin invocation context, exact pane and
agent records, pane process information, and the bundled API schema. It did not
invoke Conductor assemble, reconcile, harvest, teardown, or stand-down. Cleanup
closed only the disposable workspace; subsequent pane and agent lookups returned
`pane_not_found` and `agent_not_found`.

## Required identity map

| Required field | Exact source in Herdr 0.7.5 | Probe result | Stage 1 rule |
|---|---|---|---|
| Workspace ID | `HERDR_PLUGIN_CONTEXT_JSON.workspace_id`; `pane.get.result.pane.workspace_id`; `agent.get.result.agent.workspace_id` | Available and equal in the focused disposable workspace | Require exact equality; no workspace parsed from a pane-name string. |
| Pane ID | `HERDR_PLUGIN_CONTEXT_JSON.focused_pane_id`; pane and agent `pane_id` | Available and equal | A recorded pane ID is only one tuple member, never close authority. |
| Terminal identity | pane and agent `terminal_id` | Available and equal | Require exact `terminal_id`. The live macOS process response omitted optional `tty`, so tty cannot be required. |
| Agent session | pane and agent `agent_session.{source,agent,kind,value}` | Available after agent start | Require exact object equality. Absence before detection is capability unavailable. |
| Agent name | `agent.get.result.agent.name`; matching `agent.list` entry | Available for the explicitly named Herdr-started agent | Require the run-unique recorded name and exactly one matching list entry. Unnamed detected agents are ineligible. |
| Canonical cwd | plugin context `workspace_cwd`; pane and agent `cwd` plus `foreground_cwd` | Available and equal in the probe | Resolve every path physically; also verify Git worktree/common-dir identity. Any null, divergence, or noncanonical mismatch refuses. |
| Run ID | pane and agent `tokens.conductor_run_id` after `pane report-metadata` | Available only after Conductor publishes and reads it back | Generate a bounded unpredictable run ID, report it with source `structupath.conductor`, then require exact read-back in both views. |
| Resource generation | pane and agent `tokens.conductor_generation` after `pane report-metadata` | Available only after Conductor publishes and reads it back | Generate a fresh resource generation per creation attempt and require exact read-back. Do not use `pane.revision`. |

The plugin invocation context itself does **not** contain terminal ID, agent
session, agent name, run ID, or resource generation. Stage 1 must resolve the
workspace from context and then join it to strict pane and agent snapshots. It
must not treat context alone as close authority.

## Metadata and generation findings

Herdr's `pane.report_metadata` accepts up to sixteen bounded token names and a
per-source sequence. Reporting `conductor_run_id` and `conductor_generation`
with source `structupath.conductor` made both values visible in exact pane and
agent records.

A stale sequence test reported a different run token at sequence `0` after the
accepted sequence `1`. The command still exited `0`, but the live token remained
unchanged. Therefore Stage 1 cannot treat metadata command success as evidence;
it must read back the complete tuple after every report.

`pane.revision` advanced from `1` before the agent started to `6` after ordinary
terminal and agent activity. It is mutable pane output/state revision, not a
resource incarnation, and must not substitute for Conductor's generation.

Returned pane tokens are flattened and do not carry their reporting source. They
are cooperative same-user coordination metadata, not authentication. The run
journal and private JSON state remain the source of Conductor's recorded claim;
live tokens are an additional equality check against accidental foreign, stale,
or recycled resources.

## Hard boundary: close is not conditional

The bundled protocol schema defines `pane.close` with only `pane_id`. Herdr
`0.7.5` offers no expected terminal ID, agent session, revision, run token, or
generation parameter for an atomic conditional close.

Stage 1 can satisfy the program's required pre-close comparison by reading and
matching the complete tuple immediately before `pane.close`, but a same-user
process can still race that snapshot. This is a documented TOCTOU boundary, not
a security guarantee. Conductor must hold its own repository mutation lock,
refuse any mismatch, and keep stand-down disabled until B3 implements and tests
the final re-read. It must not claim atomic pane ownership or protection against
a malicious same-UID process.

## Decision and B1 constraints

B0 found a viable identity source for every required tuple member, with run and
generation supplied through Conductor-owned live metadata. B1 may proceed under
these non-negotiable constraints:

1. Resolve repository/workspace only from strict plugin context plus physical Git
   identity. Never fall back to `CONDUCTOR_REPO`, ambient `$PWD`, or newest-global
   state.
2. Generate run-unique agent names, run IDs, and resource generations. Journal
   intent before creating a pane or agent and observed identity after each result.
3. Publish run/generation metadata and read it back before marking a resource
   usable.
4. Require exactly one pane and one named agent and exact equality across
   workspace, pane, terminal, session, canonical cwd, run, and generation.
5. Return capability unavailable or ambiguous on every missing, malformed,
   duplicate, foreign, or stale field with zero close, remove, or merge.
6. Keep legacy stand-down disabled. B3 must add the immediately-before-close
   re-read and mutation-spy negative suite before any replacement pane-close path
   is enabled.

No Browser merge, release, or evidence promotion is authorized by this report.
